# 配置驱动开通流程的实施与验收

适用于模板选装、职责实例化、连接器准备等跨前端、Agent 与平台节点的流程。以下是设计和核验方法，不表示任何具体环境已经跑通。

## 1. 先复原真实顺序

1. 从用户实际入口打开详情、选择模板、查看初始化表单。记录字段、默认值、校验、提交文案和最终确认点；同名详情可能有只读/可编辑两种入口，不能按名称推定功能一致。
2. 沿按钮回调追到消息构造、Agent SOP、草稿协议、确认 API、后端事务、异步安装、实例化和结果回读。分别列正常路径与 fallback。提示词写着“绑定刚创建的实例”不证明 API 或数据库确有该绑定。
3. 列出副作用发生点：下载包、创建 profile、登记职责、启用服务、授予业务范围。核对它们是否发生在相应确认之前，以及取消/重试是否留下无归属资源。
4. 优先修通现有开通负责人使用的 SOP 和工具，不将端到端责任拆成各层自行决定的一段。管理实例名与规范包名、本地分类路径与服务器资源名分别核对，不能按短名猜目录。

## 2. 确认与参数合同

- 把表单值和对话补充值合并为一份待确认快照；已填值直接复用，只追问缺失、歧义或冲突。用户确认必须对应同一份参数，不得悄悄刷新候选后继续执行。
- 明确草稿 ready 只表示可确认，不表示 profile 已创建或业务已就绪。先检查原始助手消息是否包含草稿协议，再检查 UI 是否解析出对应确认卡及其状态，最后核对确认请求与平台回执；消息里出现 `%%duty-draft:v1` 或 ready JSON 不证明前端已保存可提交草稿。覆盖刷新、历史消息加载与职责切换后的恢复，防止只在流式回复期间可确认。
- 用户文字确认未推进时，先核对接收该轮的 DE、profile、会话与待确认快照；界面可见旧对话不证明当前模型继承了原草稿。只有已观察到提交被平台受理且仍 pending，才把等待归为异步延迟；空绑定记录本身不能证明提交发生过，不让用户反复发送“确认”或重复查空对账。
### 草稿协议解析故障的定位与回归

1. 从真实助手消息提取最小脱敏协议块，保留大小写、换行、围栏位置与结束标记；用程序核对字节，不把浏览器排版或转述中的小写当成原始大小写证据。
2. 将同一块分别送入解析、历史扫描/恢复和展示剥离函数，查清是哪一步失败；JSON 完整不等于外层协议完整。重点覆盖围栏粘在标记行、模型用闭合围栏代替协议结束标记、正常标记对、裸块与 JSON 中途截断。
3. 用真实坏块形态建立旧实现必失败的回归，再验证修复后正确恢复待确认载荷、清除原始协议且保留后续正文；补测同条消息后续含无关代码围栏的负例，防止宽松结束符吞掉正常内容。容错仅恢复草稿，不绕过 schema 校验、确认状态或业务授权。
4. 在独立临时副本验证旧实现与修复实现，不对共享活工作区执行 stash/还原来取得红证，因为文件内可能混有其他执行者的未提交成果。

- 确认后用稳定职责标识跟踪创建和重试；若必须预创建资源，先定义归属和取消处理，不依赖模型自觉清理。
- 将 Agent 定位为履职编排者，副作用经权限受控的确定性工具执行。会话不可用时显式失败并保留草稿，不静默绕过该负责人或可信确认直接创建。
- 不把唯一键冲突直接称为完整幂等；重复确认后应能定位原职责、原实例及其状态，不重复造资源。

## 3. 缺包是正常选装分支

1. 分开判断服务器已发布/启用、本地包存在、本地可实例化；服务器清单可选不等于目标实例已装。
2. 本地缺包时复用可信的服务器下载/节点安装通道，限定当前目标实例和规范版本；不要要求用户手动复制，也不要借其他 profile 的包或凭据。
3. 记录安装指令标识，消费 pending、成功、失败、过期等真实终态。只有成功终态加目标本地版本核对通过，才允许报告安装完成并继续实例化。
4. 不以 spec.yaml 提前落盘作为安装成功：解压可能尚未结束，登记脚本或 smoke 可能随后失败。增加故意先写 YAML、后返回失败的负例，以及持续 pending、超时重试、终态丢失与完整成功测试。
5. 逐层核对节点执行期限、服务端等待期限和调用工具期限；调用方超时不等于底层停止，重试应优先接续仍有效的原指令，不能无条件再下发。
6. 状态不可得时如实报告未确认完成，不能降级为文件存在即成功。对状态查询强制目标归属，只开放当前 DE 的安装指令，不借管理面扩大为任意节点命令查询。

### 工具定位与会话执行边界

1. 工具缺失报告与部署回执冲突时，先只读建立实例标识、部署根、HERMES_HOME、会话 CWD、工具后端命名空间和解释器的对应表。先定位再判断缺包：只在 home 搜索会漏掉部署根；目录名称也不必等于原地升级后的实际版本，应回读 manifest 与包版本。
2. 修复 SOP 时从已存在且有启动注入证据的配置确定工具和解释器，不依赖仓库根 CWD、系统裸解释器或具体实例路径。对部署根和 Agent 解释器目录分别检查，所有路径带引号；缺注入明确失败并保留草稿，不全盘搜索、借其他 profile 的包或让用户猜安装位置。
3. 沿真实链路检查启动脚本导出、服务加载优先级、Agent 所在进程、terminal backend 的环境过滤和进程派生。核对目标容器的实际 Agent 快照，不用宿主检出的代码替它背书；诊断环境变量时只读取必要键，不输出整个进程环境。
4. 将单次 shell 的定位赋值与工具调用放在同一调用块，每个独立 terminal 轮次重新定位，除非已实测局部变量或函数可持久化。工作目录或导出变量能保持，不证明 shell 数组、函数和未导出变量也跨轮存在。
5. 测试分两道门：先从 SOP 提取实际执行块，覆盖非部署 CWD、含空格路径、可信解释器回退、缺注入无落点，并证明旧写法会失败；再由目标模型会话在不人工注入环境、不硬编码实例路径的条件下完成至少两轮只读定位和工具调用，留原始工具轨迹、退出码、版本与实例边界。前一道通过只允许交付构建，不替代后一道运行验收。
6. 规范升级后区分运行文件更新、新会话加载和旧会话续接。验证优先使用限定只读指令，不清原聊天、不重建 profile、不为验证工具路径擅自创建业务职责或调度；只有新会话被覆盖时，将旧会话续接标为未测。

## 4. 实例绑定与运行消费

### 先核对根目录语义，再验证业务回执

1. 对同一实例分别记录部署根、DE 级 home、profile home 和会话 workspace。不要假定同名 `HERMES_HOME` 在 WebUI、模型 terminal 与 CLI 中都表示同一目录；从目标模型工具调用只读打印必要路径键，禁止输出全量环境。分别记录路径值与身份变量是否设置，不能因本机设置了 `HERMES_PROFILE` 就假定目标会话也设置；缺省值也须按实际返回验收。宿主或另一 Profile 的实测不能代替目标子进程实测。
2. 将工具定位和业务数据定位分开验证：能调用 `spec_tool` 不证明台账、对账状态、槽值解析及其 Hermes 子进程使用同一 DE 根。沿路径 helper 追踪所有消费方，检查重复 `profiles/<name>` 段、跨实例路径和符号链接边界；不要仅修 `list` 的显示路径。
3. 覆盖 DE-home/profile-home 两种入口、非默认管理职责名、身份不一致、缺少证据、嵌套路径和 symlink 越界，并以旧版真实子进程执行证明负例能捕获原缺陷。目录结构恰好吻合不是普适身份凭证；不能将当前已知路径下通过的规则扩写为任意目录都安全。
4. 真实模型至少完成两次实际执行，而不只发送两次调用。若框架返回 byte-identical 去重提示，该次不计执行；对只读验证可加无副作用的轮次标识重跑，不借此绕过有副作用操作的幂等保护。逐轮核对原始 stdout、工具退出码、台账真实条目和绑定状态，`EXIT=0` 与“台账不存在”同时出现仍是业务验证失败。

- 复用 profile 前核对来源规范及当前职责参数；同规范不是同一职责的证明。快照不一致时明确冲突或使用独立落点，不能静默沿用旧值，也不能覆盖其他职责的配置与授权。
- 提供可确定回读的结果：职责标识、profile、规范版本、实际应用槽值、状态和错误。区分 origin 记录、生成产物与运行会话；读到 origin 只证明记录值，不自动证明每个服务已加载。
- 将管理 profile 台账与平台职责绑定登记分开断言：管理 profile 已存在不保证有同名业务职责绑定。只读 `duty-binding` 返回 `ok=false`、空 records 和非零退出码时保留原文与真实退出码，不伪报 bound，也不为了让探针通过创建绑定。该结果可证明错误被如实暴露，不能当作业务开通成功；创建后的验收仍须查询实际职责标识。
- 验证参数消费方真实可达：服务文件、llm_expose 声明和测试存在仍不够，还要检查 adapter 的 --only/--only-ops、注册表、实际工具发现与 SOP 触发点。
- 对已填项目和节奏，断言后续直接匹配候选/预览时间，只进行必要消歧与可信授权确认。参数描述责任范围，不代替外部账号认证、业务授权或调度创建。
- 分开平台人用户、DE 机器身份、外部系统用户三域。owner 查询可以明确目标 DE 并服务端校验归属；机器回读限制本 profile/职责，不跨域比较 uid，不在通用层解析某业务规范私有授权文件。

## 5. 从测试到部署的交付门槛

- 分开文本合同测试、mock 逻辑测试、真实 HTTP/权限接缝、已部署浏览器端到端和外部上游业务验证；前一层通过不能冒充后一层。
- 缺少外部凭据只阻塞真实上游验收，不阻塞检查本地白名单、调用接线、字段契约和隔离测试；不能以“待用户”代替尚未完成的接线工作。
- 修测试夹具时先核模块何时解析参数：导入时已固定的 CLI 参数须在模块加载前注入，加载后再改 `sys.argv` 不会改变已解析对象；对凭证拒绝负例同时断言网络调用未发生，避免测试绕过目标分支后碰到真实网络而假绿。
- 给缺省参数与显式空值分别建用例：需要测试“未配置”时，用默认值或独立 sentinel 区分省略参数与传入 `None`，不要在 helper 开头统一补默认值把负例抹掉。重复建夹具还须验证目录与文件状态幂等，并对每个权限负例显式设置和读取模式，不能假定重写文件后权限不变。
- 将构建脚本放在其清理目录之外，先校验清理目标与脚本路径不重合；脚本启动时删除 staging 会连自身文件一起删除，进程可能继续执行但后续修补或重跑已无原脚本。
- 固定所有受影响交付物，而不只构建前端。工具、管理规范、业务规范和平台服务分别注明实际发布通道、版本、绝对路径与哈希；部署者不能从漂移工作区猜版本。
- 未获提交授权时，使用基线 revision、精确 diff、新增文件快照及产物哈希建立可追溯性，不因 reviewer 建议就 commit/push。共享工作区有并行改动时，按下面的干净制品步骤处理，不靠声明排除代替实际排除。

### 干净制品与增量复审

1. 固定基线 revision 和本次批准文件白名单；用 `git archive <revision>` 导出到独立 staging，再只复制批准差异及必要新增文件。不要在活工作区执行还原、stash 或覆盖来“清理打包”。
2. 用 `zipfile`/`tarfile` 枚举实际包文件集合并逐字节比对：本卡变更等于批准内容，未批准并行文件等于基线或不入包；将打包器固有的 registry 过滤、生成文件等列为显式转换，要求未解释差异为零。用 `git show <revision>:<path>` 取得基线字节，以 sha256 核对活工作区并行文件打包前后未变。独立审查应自己计算，不只运行工程师的自证脚本。
3. 对哈希命名前端资源，先从基线与候选镜像只读导出静态目录，逐文件计算 sha256 并枚举新增、删除、改名及内容变化；再用 `git diff --no-index --word-diff=porcelain` 核对每对变更 bundle，将真实代码差异与 chunk 引用改名逐项对应。只有所有运行时差异都可归因于批准源码，才允许声称无夹带；改名资源数少、大小相同或抽查特征串均不够。区分源码 HEAD、当前工作树、基线镜像与候选镜像四层；报告明确哪些逻辑原本在线上，不能把 Git 未提交自动解释为本次新增。
4. 为重打制品使用新目录和 MANIFEST，保留旧制品；先读打包脚本参数解析与默认值分支，再决定版本策略。de-dev 的 mac/linux `pack.sh --version X.Y.Z` 可显式指定版本，Git 提交计数只是缺省值，不为升版擅自 commit。使用原已审 staging 和固定 `--agent-ref` 重构建，用 `zipfile` 归一顶层版本目录后逐条目比对；若代码未变，差集只能是明确批准的版本/构建时间等生成元数据。完整 sha256 不能替代唯一版本准入：发布前读真实 `versionExists` precheck；同版不同 sha 停止，不覆盖、不绕闸门，实例侧同版跳过和缓存规则也要核对。未变化组件沿用原包及原哈希，注明沿用而不假称重建。
5. 将源码历史归档与可部署 payload 分开；含并行 diff 的归档只供追溯，不能作为 builder 的构建输入。报告与包内都检查凭据和安装态；哈希匹配只证明文件没变，不证明范围获批或内容安全。
6. 核心审查已通过而只剩少量退回项时，以差异合同修正、复跑相关测试、核对重建包及沿用组件，然后做一次独立增量复审；不要为文案或打包收尾重新探索整个架构。

### 登录与会话验证通道的恢复

1. 先在实际执行者的浏览器导航目标 origin，再用 `browser_vault list` 检查可用登录；区分已登录浏览器、本站可用条目、锁定后端与跨 Profile 不可见。只记录必要身份和成功状态，不读取凭据文件或把秘密传入普通浏览器脚本。
2. 已确认 worker 无可用通道时，不因换了一张测试卡就重复同样尝试。若 Leader 交互会话有本站已授权条目，可在原任务授权范围内补做限定验证：导航目标页 → 本会话重新 list → 填非秘密账号标识 → vault fill → 提交 → 读回登录后的页面身份。补做仅证明该交互通道，不把 worker 的 BLOCKED 改写为 PASS。
3. vault 报 origin mismatch 时，先检查浏览器当前页与 vault 报告的 origin；若指向空白或新标签页，重新将当前标签导航到精确目标 origin、确认页面后再调用 fill。保留 origin 绑定，不改凭据绑定、不从其他条目提取密码；登录后的页面读回才是恢复成功证据。
4. 点击工作台等可能打开新标签的入口后，先用 `cdp('Target.getTargets')` 核对实际新页面 URL 与 opener，再核对目标 DE/profile 映射；当前标签未跳转不等于点击失败，打开名为 Hermes 的页面也不证明进入了目标实例。切换职责、开启话题和发送验证消息均是异步动作：每一步先读回选中的职责与新会话，再执行下一步；首次点击无即时变化时等待并核对会话列表/回执，不直接二次点击，因为请求可能已成功而 UI 尚未更新。发送前固定目标 DE、profile 与会话；发送后核对消息落点及真实模型会话标识，页面显示历史消息不能单独证明模型复用了旧上下文。
5. 只发送一次范围明确的只读验证指令，包含禁止安装、实例化、调度及修改原草稿的边界。出现“处理中/内部重试”时不重发、不把提示当作工具执行成功；按原会话收集工具调用、退出码和终态。认证恢复、消息送达、工具成功与业务创建分别判定，未拿到原始回执保持未验证。

### 升级保留态核证

1. 在升级前读取当前登记表、启用位、已安装包与固定版本、安装终态记录、管理台账和用户数据基线；代码树与数据面分别记录。提前检查基础包安装器是否替换整个规范目录，因为只检查 home 数据面会漏掉部署树中的本地安装态。
2. 将“文件存在 / 已登记 / 已启用 / 安装终态闭合 / 已绑定 / 可履职”分别列断言。升级后按结构化字段和必要文件指纹比对，不能把重新安装后默认禁用称为原态完整保留，也不能用 mtime 无明显变化替代业务调度或草稿关键字段核对。
3. 出现保留态差异时，先记录原值、现值、影响范围和授权，再安排 builder 走已存在且查证过的受控恢复机制；不要假设存在 enable 子命令，不整份覆盖注册表，不靠创建职责来触发恢复。精确恢复升级前已证实的启用位不等于授予外部业务访问或创建巡检；不得借恢复扩大授权。执行前明确消费方何时读取配置、受支持的显式应用步骤及当前部署规则是否允许该方式；“实时读取即生效”描述的是机制，不是合规豁免。仅有直接改运行文件的旧说明而无法满足当前规则时，先报告缺口，不先写后补理由。安全恢复方法未验证前，只记录差异与待决门，不把尝试写成可靠操作配方。
   - 原始备份和字段指纹必须在应用前取得，先核对备份内容与当时现状再写入；应用后取得的副本不能命名或报告为 before。若快照顺序出错，保留原工具输出作为有限证据，将逆向生成的副本标为 reconstructed，明确无法独立追溯的范围，禁止以重构 diff 证明全部其他字段当时未变。
4. 在独立验收卡上追加恢复卡依赖，并读回门控关系；尚未恢复的状态不得随部署卡 done 自动变成验收通过。恢复后重新核对其他登记条目、已审代码哈希、用户数据与非目标实例未变，完整业务创建验收仍单列。

### 升级器保全与失败恢复的工程核证

1. 先枚举升级器实际替换目录和备份/回放白名单，再将本地规范树、未登记树、registry 启用位、安装终态与数据面逐项映射；旧目录暂存不等于持久保全，须追踪下一次升级是否清理它。通用包不得混入某实例的安装态。
2. 将取包、解压、基础 registry 语义检查和同路径冲突检查放在 stop、移动备份及清理旧回滚窗口之前；负例须断言实例未停、原文件未动，而不只断言返回错误。无本地态实例另测正常基础包演进，避免保全护栏变成禁止所有升级。
3. 回放旧 registry 前比较新包基础条目与当前对应条目的语义，冲突即拒绝；不得无条件整份旧表覆盖新包，也不得把所有“当前有、新包无”的键永久当成本地新增，因为基础包可能移除旧条目。无法证明来源时保持冲突显式，不声称通用合并已经解决。
4. 对每个 stop 后的错误出口注入确定性故障：备份失败、旧目录改名失败、新目录就位失败、新版启动失败、恢复旧版启动失败。恢复函数按磁盘真实状态定位旧目录，绝不误启动半途新目录；恢复后补齐原启动参数并探活。恢复失败必须同时保留原错误与恢复失败明细，禁止忽略 rename/start 错误后仍宣称已重启。
5. 优先用隔离真实升级链和受控 startup 夹具测试；文件权限或时序无法可靠注入时，可用仅测试构建启用的故障闸门，并从 release 二进制验证闸门未打入。用移除恢复调用、强制成功文案等最小变异证明状态断言和错误断言各自会红；在独立副本做变异，恢复后校验源码哈希及夹具进程零残留。
6. 修正代码后构建新唯一镜像，不覆盖前一已审 tag；保留仍在运行的真实回滚镜像，未部署候选不能冒称已运行基线。分别交付镜像 ID、二进制指纹、源码基线与批准 diff；本地 image ID 不冒称 registry manifest digest，符号/时间窗绑定不冒称字节级可复现构建。

### 移交真实环境验收

1. 部署前由 builder/tester 对齐测试前置状态：目标实例、包是否已安装、原有职责/profile，以及哪一步保留给会话自动执行。明确唯一的真实创建执行者；Leader 辅助有登录态的浏览器验收时，由 Leader 独占确认与业务发送，tester 收集断言和证据，不并发点击或重复创建。若 builder 已完成自然缺包安装，保留 commandId 终态证据，并将会话自动恢复缺包标为未测；不要删除现有包制造未经批准的故障。
2. 将 UI 移交分成“取得会话”“执行交接副作用”“传输送达”三层。会话创建失败不等于发送失败覆盖；副作用回调也要有异常兜底，并测试抛错时不触发直接创建 fallback。部分执行后不得统一声称草稿完整保留或什么也没发生。
3. 用真实平台登记的规范全名贯穿 help、SOP、台账、下载和安装路径；未匹配到名称与已登记但未启用分开报错。对短名输入列候选或要求消歧，不静默补分类路径，避免把命名错误引导成启用权限问题。
4. 部署备份也受保密和位置授权约束：整实例备份可能含身份、令牌与日志，不因叫备份就允许导出到宿主 scratch 或任务附件；先限定位置、权限与保留策略，报告只给路径和摘要。回滚方案必须沿用当前部署约束，不能恢复可修改 bind mount 来重新引入热更新；未经演练明确标注未演练。
### 浏览器提交后的分层回执与故障定位

1. 提交前逐步查看确认卡中的规范、职责名、全部已填槽值和可选字段，保留原快照；明确本次唯一提交者。点击一次后观察该次产品请求，不通过另发 API 请求制造替代成功，也不因 UI 尚未变化重复点击。
2. 记录目标创建请求的 method、无敏感查询串的 URL、HTTP 状态、业务 code 与生成的职责标识；再用产品的列表/详情 GET 回读同一标识和槽值。HTTP 成功、业务成功与持久读回分别断言。需要页面内观察 fetch 时只针对目标接口使用 `response.clone()` 读取响应，不记录认证头、cookie 或无关响应，不改变原请求行为。
3. 分开检查平台职责目录与实例运行职责目录：详情中出现展示名、enabled=true，只证明平台记录存在；必须再核对节点派发 command 的真实终态、实例绑定与管理台账，并刷新 UI 检查新 profile 可选、选中身份正确。运行列表仍只有原有 profile 时，把断点定位在落账之后，保留原职责标识交给后续排障，不删建、手工实例化或补绑定来凑通过；静态调用链存在不能证明异步任务已执行。若采用周期对账，读取目标实例实际配置与最近对账日志，串起平台创建、安装终态、对账启动、binding created 的时间线；在已证周期内有界等待后复核，超过预期或出现明确错误即转排障。不要把某次观察到的默认周期硬编码为所有环境的等待时间，也不要把技术上预期的延迟自动判成良好体验。
4. 先读取调度 SOP，区分“初始化时自动创建”与“预填节奏、授权有效后预览并另行确认创建”。前者须检查真实任务，后者须分别验证槽值已消费、未越过确认擅建，并把实际任务创建保留为待完成项；不能将未建任务误判为初始化缺陷，也不能把符合分步合同称为巡检已运行。再同时检查平台调度字段和规范实际采用的运行时调度存储；`scheduleCron`/`scheduleJobId` 为空不证明所有后端都无任务，槽值进入 origin/applied_slots 也不证明已有调度。
5. 将草稿隐藏与后端防重放分开验收：分别检查同页刷新、重新登录及独立浏览器中的恢复行为；本地墓碑可能只在当前浏览器有效，单次刷新后消失不证明全局幂等。已落账的旧卡再次出现时先读回稳定职责标识，记录缺陷，不为验证而重复点击；仅存在唯一键或返回冲突也不等于可恢复原职责及完整幂等。保留职责落账响应、运行目录回读和 selector 截图的独立证据；截图生成后立即复制到持久证据目录，避免临时路径被下一次覆盖，只存脱敏目标载荷并标明实际执行来源。
6. 最后才在选中的真实 profile 中发送一次授权范围内的业务查询，核对模型原始工具回执与结果。先从目标实例会话索引按本次独特只读指令定位 session_id，再检查该会话实际 profile、消息与工具轨迹；不要只凭下拉标签或界面混合历史判断模型归属。读取 JSON 前先判断顶层是索引列表还是会话对象，仅提取必要字段，不倾倒全部会话或秘密。
7. 查询持续“处理中”时，记录同一会话的最近进展、工具阶段与 pending/stream 标志，在一个有界观察窗口后转交执行链诊断，不用反复截图耗尽预算。单个 `is_streaming=false` 或非空 `active_stream_id` 不能独立证明卡死；首段技能读取文案也不能证明业务工具成功。沿原请求核对原始工具回执和最终响应，不重发、不伪造成功；尚未定位的故障只保留取证边界，不将未奏效尝试写成可靠恢复配方。
8. 将“平台创建成功 / 自动绑定完成 / profile 显示可切入 / 等待外部授权 / 真实业务查询成功 / 调度已配置”分别报告，不把包哈希、单元测试、详情展示或模型话术当作整个开通目标完成。
