# 四类任务卡模板（2026-10-17 固化）

所有派发给执行者的卡必须包含以下**五段必填**，缺任何一段视为合同不完整，执行者应 `kanban_block` 而不是猜：

1. **目标** —— 要达成什么；对总目标的作用（一句话）
2. **验收标准** —— 部署卡式：`- [ ]` 逐条可勾选，每条以**读回证据**为准（"命令退出码不算证据"），必须包含正向验证 + 非回归两面
3. **执行任务规范** —— 角色边界、红线、必须遵守的约定
4. **执行步骤** —— 编号步骤，含不可跳过项
5. **执行完成后报告的标准规范** —— 报告必须包含的字段，写入卡 comment 或交付文件

**执行报告硬规则（2026-10-17 定）**：执行任务完成后**必须返回执行报告**，报告开头为两个必填块，缺任一块视为未完成交付：
- **验收标准完成情况**：把卡里的验收标准逐条复制，已完成打 `- [x]` 并附该条的读回证据（命令/输出/路径）；未完成保持 `- [ ]` 并写明原因。禁止只写"已全部完成"的总结性一句话。
- **目标实现情况**：达成 / 部分达成 / 未达成 + 一句话依据；部分达成或未达成时列出剩余工作与建议。

底座公共字段（每张卡另有）：负责人（真实 Profile）、背景与输入（含参考文件绝对路径）、范围与约束、前置依赖（父卡 ID 或"无"）、优先级、截止时间（未指定则写"未指定"）。body 必须自包含：执行者不读 leader 与用户的聊天记录就能开工。

依赖链：实现卡 → 部署卡（parents=[实现卡]）→ 测试卡（parents=[部署卡]）；审查卡 parents=[部署卡 或 实现卡]。父卡 done 只解除调度依赖，子卡执行者仍须按本卡规范独立核实前置成果。

## 一、实现卡（assignee=engineer）

```markdown
## 目标
<要实现的变更>；对总目标的作用：<一句话>

## 验收标准
- [ ] 产物已构建且版本可追溯：镜像 tag 固定到提交号/digest，或发布包 + MANIFEST.json（浮动 tag 不算通过）
- [ ] 适用的测试真实运行并通过（读回测试输出原文；开发服务器启动成功 ≠ 生产构建通过）
- [ ] 缺陷修复类任务：原问题的复现路径已验证消失（附修复前后的对照证据）
- [ ] 改动范围核对通过：git diff 逐文件核对，无任务外的顺手优化、无无关文件变更
- [ ] 部署输入三要素齐全并写入交付：Compose 项目、目标服务名、产物绝对路径

## 执行任务规范
- 先读任务合同、项目 AGENTS.md、真实代码与既有构建测试约定，再动手
- 遵循项目已有架构、命名、依赖管理和测试方式；不另起一套，不扩大重构范围
- 并行修改同一项目时使用明确的文件归属/独立工作区，不覆盖他人未提交变更
- 构建约定：禁热更新；产物固定版本；只构建受影响服务；不启停生产容器；**不部署**（部署归 builder）
- 遇需求缺口先报告 Leader；常规细节自行决定并记录在卡里
- 不做任务外优化、不动无关数据；凭证永不写入报告

## 执行步骤
1. 读取合同、AGENTS.md、相关代码与测试约定，确认目标、范围、接口与验收标准
2. 识别与其他任务的文件/接口冲突，需要时申请独立工作区
3. 实现最小完整改动
4. 按变更风险选择有价值的测试（优先项目已有测试；不用镜像实现的测试充数）
5. 运行测试与生产构建，保留命令与输出
6. 产物固定版本（镜像钉提交号/digest 或发布包+MANIFEST）
7. 自查改动与证据
8. 交独立审查：已有依赖本卡的审查子卡则 kanban_complete 放行；否则 kanban_request_review（注意同卡 review 不是独立审查，独立审查须另建 reviewer 卡）

## 执行完成后报告（写入卡 comment / 交付文件）
**开头必填两块（缺任一块视为未完成交付）**：
① **验收标准完成情况**：本卡验收标准逐条 `- [x]`（附读回证据：命令/输出/路径）或 `- [ ]`（附原因）；
② **目标实现情况**：达成/部分达成/未达成 + 一句话依据；未全达成列出剩余工作与建议。

其余字段：
- 任务 ID 与执行时间
- 改动摘要 + git 提交状态（分支/commit/未提交清单）
- 测试与构建：真实命令 + 输出关键行（不是转述）
- 产物：绝对路径 + 版本标识（提交号/digest/MANIFEST）+ 目标 Compose 项目与服务名
- 限制、已知问题与未完成项
- 下游（builder）部署输入清单
```

## 二、部署卡（assignee=builder，parents=[实现卡]）

```markdown
## 目标
<把什么版本送进什么环境>；对总目标的作用：<一句话>

## 部署输入（缺任何一项 builder 有权拒卡 block）
- 产物绝对路径：<...>
- 版本：<提交号 / 镜像 digest / 发布包版本>（"大概是这个版本"不算）
- 目标 Compose 项目与服务名：<...>
- 回滚手段：<上一版本标识 + 回滚命令/入口>

## 验收标准
- [ ] 目标服务版本已读回验证：容器实际镜像 digest / 包版本与部署输入一致（命令退出码不算证据）
- [ ] 健康状态已读回验证：health/status 端点或等价真实证据
- [ ] 非回归验证：非目标容器的 ID 与启动时间与部署前基线 diff 无变化
- [ ] 回滚路径就绪并已记录（上一版本标识可取、回滚入口可用）
- [ ] 合同要求的部署后冒烟入口可达（由 tester 执行的除外，此处只验服务自身起来）

## 执行任务规范
- 拒绝无版本产物；不部署无法追溯版本的任何东西
- 变更前必须留证留退路：`docker ps -a` 基线快照（目标+非目标容器）
- 显式构建并替换受影响容器：`docker compose … up -d --no-deps <services>`；不触全项目脚本入口（除非合同明确批准其副作用清单）
- 不改业务代码；需要改代码才能部署成功 → 写明原因退回 engineer，不顺手改
- 结论门：预建依赖审查时，审查结论未明确准入通过则停止并回报 Leader
- 失败即回滚，不带病上线

## 执行步骤
1. 确认部署合同（目标服务、版本、影响面、停机要求、回滚手段、授权边界）
2. 变更前快照：docker ps -a 基线 + 关键数据备份
3. 显式构建/替换目标服务（--no-deps）
4. 读回验证：版本 digest + 健康状态
5. 非目标容器 diff 核对
6. 写部署报告（字段见下）
7. 异常时按既定回滚路径回滚并报告

## 执行完成后报告（按 builder-deploy-ops §7 部署报告模板）
**开头必填两块（缺任一块视为未完成交付）**：
① **验收标准完成情况**：本卡验收标准逐条 `- [x]`（附读回证据：版本读回/健康读回/diff 结果）或 `- [ ]`（附原因）；
② **目标实现情况**：达成/部分达成/未达成 + 一句话依据；未全达成列出剩余工作与建议。

其余字段（至少含）：
- 任务 ID、部署时间窗、执行人（builder）
- 部署输入核对：产物路径 + 版本 + 目标服务（与合同逐项对照）
- 执行记录：真实命令与关键输出（部署前后各一份）
- 验证证据：版本读回、健康读回、非目标容器 diff 结果
- 回滚路径：上一版本标识 + 入口 + 当前是否已就绪
- 异常与处理：本次遇到的失败/重试/回滚动作
- 未决事项与需 Leader 决定的事项
```

## 三、测试卡（assignee=tester，parents=[部署卡]）

```markdown
## 目标
<对什么对象验证什么行为>；对总目标的作用：<一句话>

## 被测对象
- 环境 URL：<...>
- 目标版本：<部署卡实际生效的版本，须与部署读回证据核对一致>
- 账号角色（无秘密）：<...>
- 授权的数据范围与操作：<...>

## 验收标准
- [ ] 每条用例有可判定断言，状态只用 PASS/FAIL/BLOCKED/NOT_RUN，逐条留证
- [ ] 断言失败记 FAIL，无放宽断言迁就结果（执行完成但结论可以是失败）
- [ ] 证据绝对路径真实存在且可复核（截图/trace/日志/接口响应）
- [ ] 被测版本与部署卡生效版本核对一致（测错版本全部作废）
- [ ] 报告明确列出未覆盖部分与受阻原因（未测不算通过，done ≠ 验收通过）

## 执行任务规范
- 只做测试与记录：不修业务代码、不部署、不自派修复卡、不替 Leader 宣布最终验收
- 缺被测对象要素（URL/版本/授权缺一）→ 报告派发方，不猜不编
- 测试脚本与产物只写测试专用目录（默认 workspace 下 tests/<task-id>/），不写被测系统目录
- 环境本身的修复与回滚归 builder，测试中只报告不动手
- 清理只限本任务自建的数据与临时服务

## 执行步骤
1. 读卡确认被测对象、环境、版本、授权边界；缺项即报，不猜
2. 按任务选择 SOP（tester-testing：部署后冒烟/登录权限会话/核心端到端/表单异常边界/缺陷复测回归）设计用例，每条带断言
3. 执行并逐条留证（截图、trace、日志、响应的绝对路径）
4. 汇总用例结果，出报告
5. 清理本任务自建数据，不动被测环境

## 执行完成后报告（写入卡 comment / 报告文件）
**开头必填两块（缺任一块视为未完成交付）**：
① **验收标准完成情况**：本卡验收标准逐条 `- [x]`（附读回证据）或 `- [ ]`（附原因）；注意用例 FAIL 属于执行完成但结论失败，对应目标实现情况如实写；
② **目标实现情况**：达成/部分达成/未达成 + 一句话依据（测试卡：全部 PASS=达成；有 FAIL=部分达成/未达成并列缺陷）。

其余字段（至少含）：
- 任务 ID、测试时间、被测环境 URL 与版本（附版本核对依据）
- 用例表：编号 | 用例名 | 断言 | 状态（PASS/FAIL/BLOCKED/NOT_RUN）| 证据绝对路径
- 结论：通过/失败/受阻（一句话，基于用例统计）
- 缺陷清单：每条含复现步骤、证据路径、建议 severity
- 未覆盖部分与受阻原因
```

1. 读取原始合同、验收标准、项目约定（AGENTS.md、Docker 部署约定）与实际改动

3. 检查测试覆盖是否针对真正风险；核对测试与测试本身的有效性
4. 核对测试/构建/部署证据与实际版本一致；独立复跑关键验证并记录命令

## 证据阶梯与状态语义（同步自 OMH 源码 `coordination_board/v1` + `agent_board`，2026-10-17）

源码位置：`/Users/abc/workspaces/code/oh-my-hermes`（v3.0.2，`src/workflows/coordination_board.py`、`src/workflows/agent_board.py`）。

### 核心公理：状态词是声明，永远不是证据

OMH 源码里明确列出的"完成声明词"：`done / completed / finished / complete / already_completed / merge_ready / ok / passed / success`——这些词只把工作项移出待办泳道，**永远不会进入 evidence_observed**。证据只能来自真实观察事件（observation journal 里被观测到的执行/验证/审查/CI/合并事件）。

对应到我们的卡体系：
- 卡状态 `done` + 执行者口头"已完成" = 声明。Leader 验收时以此为零信任起点。
- 执行报告里的 `- [x]` 必须对应一条**真实读回**（自己跑的命令/亲自读的文件/复跑的测试），否则该条视为 `missing_evidence`，验收不放行。
- `evidence_complete`（证据闭合）不能由状态词达成——这正是"done ≠ 验收通过"的源码依据。

### 五类证据（每张卡按适用类型分区核对，"缺什么"必须完整回答）

| 证据类型 | 含义 | 适用卡型 |
|---|---|---|
| execution | 真实执行被观测（命令跑过、部署发生过） | 全部四类 |
| verification | 验证被观测（测试/断言/读回通过） | 实现卡、部署卡、测试卡 |
| review | 独立审查被观测（reviewer 卡真实结论） | 审查卡（对前三类是验收前提） |
| ci | 构建/CI 通过被观测 | 实现卡（生产构建 ≠ dev server 启动） |
| merge | 合并/发布动作被观测 | 视合同而定（部署卡≈"变更生效被读回"） |

规则：每张卡的报告应能回答"五类中哪几类已观测、哪几类缺失"——**缺失清单必须完整，不许悄悄省略从未检查的项**。

### 六泳道 ↔ Kanban 状态对照

OMH 泳道（决策优先级排序）：`blocked → dependency_gated → active → next_ready → prepared → evidence_complete`。

- `dependency_gated` = 父卡未 done（对应 kanban 的 todo/等待父卡）；**注意：依赖满足（父进程退出码 0）也不是证据**，只是门开了
- `prepared` = 准备好但未执行——对应我们 SOUL 里的"prepared ≠ executed"
- 声明词只能让工作项**离开** next_ready/prepared，停留在 active，直到观察阶梯闭合它

### agent_board 操作契约（对 Leader 用 OMH 桥接时生效）

- `omh_agent_board` 返回的 `native_action` 只是**准备**，不证明调用或成功；必须由 Leader 真实调用原生 kanban 工具并拿到 `ok task_id` 才算数（CLAIM_BOUNDARY 原文："Prepared actions are not invocations; receipts prove only the correlated operation, not review approval, CI or merge."）
- 回执只证明"该操作发生了"，不证明审查批准、CI 或合并
- OMH 侧认知的 kanban 状态全集含 `scheduled`（停放）与 `archived`——暂停任务用 `kanban block/schedule`，不要拿 todo 当暂停



## 使用注意（实测坑）

- **同卡 `kanban_request_review` 不是独立审查**：review 通道用卡自己的 assignee 重跑。真独立必须另开 assignee=reviewer 的卡（本文档模板四）。
- 依赖方向：汇总卡应是执行卡的**子卡**（parents=执行卡），写反会死锁执行卡。
